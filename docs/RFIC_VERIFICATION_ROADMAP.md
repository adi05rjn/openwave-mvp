# RFIC verification workbench: sequential implementation plan

Research date: 2026-10-25  
Status: **proposed roadmap only — no implementation started**  
Companion: [Axiro RFIC opportunity research](AXIRO_RFIC_OPPORTUNITY_2026-10-25.md)

## Objective and operating rules

Explore a small, open-source, **reproducible RF verification workbench** that analyzes RF passive network results and, only later, orchestrates established EM solvers. The user value is defensible comparison, provenance, regression detection, and eventually public RFIC examples.

This is **not** an HFSS clone, a commitment from Axiro, or a replacement for production EDA sign-off. Do not build the next layer until the previous acceptance gate is met. Durations below are *estimates after prerequisite work is complete*, not a guaranteed calendar schedule.

## Precondition / Gate 0 — finish existing OpenWave validation

OpenWave currently implements ideal rectangular-waveguide scalar TE eigenmodes with a 2-D finite-difference solver, not 3-D driven RF simulation.

Before any RFIC module:

- Reuse existing analytical cutoff and mesh-convergence tests; publish a WR-90 TE validation dossier with commands, numerical errors, convergence plot/table, mode-index/sign caveats, and known limitations.
- Confirm the GUI, legacy CLI, JSON runner, and MCP interfaces yield consistent physical results under documented tolerances.
- Keep existing schema, educational GUI, bounded execution, output confinement, and solver internals unchanged by this research phase.
- Record why RFIC verification is worth exploring in addition to the teaching workflow; obtain initial feedback from at least two practicing RF engineers when feasible.

**Gate 0 pass:** the baseline numerical report is reproducible and linked from the README, and no existing test/interface regression is known. The [existing feedback document](REDDIT_FEEDBACK_2026-10-24.md) is the authoritative source for the earlier P0 work.

## Vertical slice (first working artifact)

A local command that loads **two public or synthetic Touchstone files**, checks compatibility, compares selected S-parameters over a specified overlapping frequency band, and writes a deterministic report:

    openwave rf-compare reference.s2p candidate.s2p --band-ghz 1:10 --output reports/example

This is an **illustrative proposed CLI**, not an implemented command.

Inputs: .s1p/.s2p, explicit frequency band, port selection, reference impedance and interpolation policy, and optional numeric acceptance thresholds.  
Outputs: machine-readable report (versioned JSON), plots (magnitude dB, phase where meaningful, optional Smith chart), worst-case and RMS error by metric/band, pass/fail status, input hashes and versions.

Do not call a magnitude-only difference a complete complex S-parameter comparison; phase wrapping, reference planes, missing frequency coverage, and Z0 normalization matter.

## Gate 1 — week 1 estimate: Touchstone analyzer and tests

Implementation candidate: isolated optional Python module using NumPy + scikit-rf, with no numerical dependency added to the existing scalar TE solver.

Tasks:

1. Parse and validate files and metadata; reject NaNs, inconsistent port count, empty band, incompatible Z0 without explicit renormalization, and malformed frequency grids.
2. Calculate S11/S21 (and S12/S22 if supplied), magnitude in dB, unwrapped phase, and complex differences. Define interpolation in the **complex plane**, not simply between dB points.
3. Emit deterministic JSON with units, schema version, selected reference plane/normalization policy, versioned settings, SHA-256 hashes, error summary, and reasoned failure messages.
4. Add tests with synthetic matched-line, reflecting-line, and known two-port cases. Example ideal matched lossless line: |S11|=0 and |S21|=1 in its valid band, with known propagation phase.
5. Test malformed input, no overlap, reversed ports, phase wrapping, unit conversion, and mismatched frequency samples.

**Gate 1 pass:** one command produces re-runnable results and CI tests check against **independent analytical/synthetic oracles** rather than snapshots generated by the code under test. No graphical interface required.

## Gate 2 — week 2 estimate: trusted solver adapter

Tasks:

1. Use an existing public openEMS transmission-line example, without changing its numerical algorithm.
2. Define an adapter interface for executable, bounded, deterministic settings and solver-generated Touchstone artifacts; preserve full console logs and solver versions.
3. Compare generated S-parameters to an analytical line model and/or a published reference under explicitly stated assumptions.
4. Sweep mesh resolution to check convergence. Record cells, runtime, memory where available, boundary conditions, port setup, and excitation.
5. Isolate optional third-party dependencies and fail clearly if openEMS is not installed.

**Gate 2 pass:** a clean user environment can reproduce one solver-to-report workflow from public inputs; results are stable under the documented numerical tolerance and improve or settle with mesh refinement. Do not claim accuracy from a single attractive plot.

## Gate 3 — weeks 3–4 estimate: first genuine RFIC passive

Choose **one public IHP SG13G2 spiral inductor or transmission-line reference**, reusing [gds2openEMS](https://github.com/VolkerMuehlhaus/gds2openEMS), the [IHP PDK](https://github.com/IHP-GmbH/IHP-Open-PDK), and their existing examples. Evaluate Palace as a second backend only if its setup and reference are feasible.

Tasks:

1. Lock GDSII, public stackup, layer mapping, material assumptions, metal thickness/loss model, ground/port reference planes, and frequency range.
2. Generate and retain S-parameters and plots. Extract a *defined* equivalent series impedance, inductance, Q and resonant behavior where the chosen circuit model is meaningful.
3. For a suitable one-port series model, illustrative formulas are L(f)=Im(Zin)/(2*pi*f) and Q(f)=Im(Zin)/Re(Zin); termination, de-embedding, topology, and sign conventions must be stated. These formulas are not universal near self-resonance.
4. Compare to published reference or measured public data when available; report differences and calibration/de-embedding limitations.
5. Document mesh and boundary sensitivity, not just a result at one mesh size.

**Gate 3 pass:** one reproducible open-process passive benchmark with clear model assumptions, reference comparison, uncertainty/limitations, and a transparent numerical error budget. No foundry qualification or tape-out sign-off claims.

## Gate 4 — week 5 estimate: parameter sweep and regression

Tasks:

1. Parameterize exactly one geometry family (e.g., inductor width or number of turns) using the existing permitted public flow.
2. Run sweeps in bounded queues with resource caps, caching based on input fingerprints, and manifests of failures/partial results.
3. Compare candidate metrics to a versioned baseline and flag regressions against **predeclared** engineering limits.
4. Plot metric-versus-geometry and cost-versus-error tradeoffs. Distinguish solver failure from failing a physical specification.

**Gate 4 pass:** two engineers can rerun the same sweep and independently derive the same comparison table within documented solver tolerances.

## Gate 5 — week 6 estimate: reviewable report and engineer feedback

Tasks:

1. Produce one portable HTML/Markdown report and machine-readable JSON. Include input links/hashes, solver parameters, mesh convergence, S-parameter comparisons, measured/published-reference attribution when used, hardware/software versions, limitations, and warnings.
2. Run the end-to-end example in CI where feasible; otherwise use unit/fixture tests in CI and document a manual full-solver verification command.
3. Give a public example and a short workflow demonstration to two or three working RF/EM engineers. Ask whether it actually reduces manual validation effort.
4. Track specific bugs or unmet needs. Only then decide whether to add another backend, PDK, field visualization, or GUI.

**Gate 5 pass:** independently reproducible demonstration plus external qualitative feedback with provenance. If feedback shows no differentiated need, stop or contribute improvements upstream.

## Proposed dependency boundaries (not yet code)

| Future responsibility | Candidate boundary | Guardrail |
| --- | --- | --- |
| RF result parsing/analysis | Optional `openwave.rf.networks` module using scikit-rf | No dependency from existing TE physics or GUI |
| Comparison and rules | Pure functions on normalized RF network data | Independent test oracles; units and normalization explicit |
| Solver execution | Subprocess adapter for openEMS (Palace later) | Time, memory, frequency, files and output limits |
| Experiments/results | Separate versioned RF schema + provenance | Do not silently reinterpret the current waveguide experiment schema |
| CLI/report | Optional `rf-compare` subcommand / separate entry point | Preserve old CLI flags and MCP tool behavior |
| Visualization | Report-generation adapter | Keep headless tests possible |

Treat GPL and other upstream licenses explicitly before including, modifying, packaging, or distributing upstream code. Prefer documented dependencies and separately installed solver executables until compatibility is reviewed. Use publicly redistributable PDK files only.

## Test matrix and numerical acceptance policy

| Layer | Reference | Required test |
| --- | --- | --- |
| Touchstone handling | Known/synthetic files | Port order, units, complex values, NaNs, overlap, Z0 |
| RF math | Analytical ideal networks | Magnitude, phase, impedance, lossless/passive behavior where applicable |
| Solver adapter | Existing openEMS example | Reproducible invocation, artifact integrity, failure/timeout |
| Numerical convergence | Mesh refinement sequence | Error/metric stabilization and disclosed non-convergence |
| RFIC passive | Public IHP example/data | Explicitly stated geometry, de-embedding, model validity and error |
| Regression | Frozen public baseline | Stable pass/fail with schema, version and threshold definitions |
| Compatibility | Existing OpenWave test suite | Unchanged scalar TE GUI/CLI/JSON/MCP results |

Do not invent a universal 1% agreement criterion. Choose accuracy thresholds *before* running a benchmark, based on reference uncertainty and numerical method; expose both absolute and relative errors and keep negative results.

## Explicitly deferred

- Native 3-D FEM/FDTD solver development, GPU acceleration, general arbitrary CAD, full PDK automation, RF transistor nonlinearity, production sign-off, optimized surrogate models, circuit co-simulation, or commercial claims.
- Redesign of current OpenWave TE solver or its MCP contract.
- Additional features before the preceding gate is documented as met.

## Decision record

| Decision | Why |
| --- | --- |
| Build verification around existing solvers first | Mature open-source EM capabilities already exist; validation workflow may be differentiating |
| Start with file-level comparison | Easiest independently testable vertical slice |
| Use IHP SG13G2 only after baseline and adapter | Public RFIC data permits credible reproducible examples |
| Protect current OpenWave educational scope | The scalar eigenmode prototype is physically different from a driven full-wave simulator |
| Ask practicing engineers before claiming demand | Axiro's tools prove relevance, not willingness to adopt this project |
